Framework internals · architecture explainer

How eve works

TL;DR — An eve app is a Nitro HTTP server whose routes come entirely from channels. Every route does one thing: hand a message to a durable session. That session runs each turn as a Workflow SDK workflow that checkpoints at every model step, so it survives crashes and redeploys and can park for days waiting on a human. Credentials and your code run in the trusted app runtime; the model's shell runs in an isolated sandbox that holds no secrets. Everything the run does is projected onto one replayable NDJSON event log: emit appends to that log, then calls channel handlers and hooks in memory — not via a message queue or WebSocket bus.

The shape of an app

Almost everything in eve is convention over configuration, and the convention is always the same: a file's stem is its id. agent/tools/get_weather.ts is the tool the model calls as get_weather. agent/channels/slack.ts is the channel addressed as slack. There is no registry file to keep in sync.

agent/
  agent.ts            ← optional. omit it and you get claude-sonnet-5.
  instructions.md     ← REQUIRED on root. the always-on system prompt.
  channels/           ← the only per-platform code. root agent only.
  tools/              ← defineTool, one file per tool
  skills/             ← markdown procedures, loaded on demand
  subagents/<id>/     ← a whole nested agent, own defineAgent
  connections/        ← MCP / OpenAPI + credentials
  hooks/              ← observe-only; fire in-process on emit
  schedules/          ← cron. root agent only.
  sandbox/            ← backend + workspace seed
  lib/                ← shared code. import-only, never reaches the sandbox.
evals/                ← sibling of agent/, not inside it

Identity never comes from an authored name or id field — it is always the path. The root agent's own name comes from the enclosing package.json#name. When something you wrote doesn't show up, eve info prints the resolved surface and its discovery diagnostics, backed by .eve/discovery/agent-discovery-manifest.json.

This repo is currently the minimum viable version of that tree — an agent.ts naming a model, and two channels:

// agent/agent.ts — the whole agent definition
import { defineAgent } from "eve";
import { openai } from "@ai-sdk/openai";

export default defineAgent({
  model: openai("gpt-5.6-luna"),
  reasoning: "medium",
});
// agent/channels/eve.ts — exists ONLY to set route auth
import { eveChannel } from "eve/channels/eve";
import { localDev, placeholderAuth, vercelOidc } from "eve/channels/auth";

export default eveChannel({
  auth: [
    vercelOidc(),        // TUI + your own deployments
    localDev(),          // eve dev on localhost
    placeholderAuth(),   // 401s in prod until you replace it
  ],
});
// agent/channels/slack.ts — gate + credentials
import { connectSlackCredentials } from "@vercel/connect/eve";
import { slackChannel } from "eve/channels/slack";

export default slackChannel({
  credentials: connectSlackCredentials("slack/eevee"),
  async onMessage(ctx, message) {
    if (message.author?.isBot) return null;
    if (message.text.trim() === "/new") {
      await ctx.reset({ reason: "user /new" });
      await ctx.thread.post("Started a fresh conversation.");
      return null;  // command only — do not wake the model
    }
    const isDM = message.raw.channel_type === "im";
    return isDM || ctx.isBotMentioned() || (await ctx.isSubscribed())
      ? { auth: null }   // allow (anonymous principal)
      : null;              // drop ambient channel noise
  },
});

Note what is absent: adding Slack required no change to agent.ts. That is the central architectural claim — the agent never learns where a message came from.

The request path, step by step

Expand each stage. The layering is strict: Nitro knows nothing about sessions, channels know nothing about the model loop, and the model loop knows nothing about HTTP.

1 · Nitro routes the request the HTTP host

Nitro hosts the HTTP routes and the workflow entrypoints. That is the full extent of its job — it supplies neither the workflow state store nor the sandbox runtime, both of which are pluggable adapters underneath it.

Every route in the app is contributed by a channel. The eve channel mounts /eve/v1/session* and does so even if no channels/eve.ts file exists; a Slack channel mounts Slack's webhook endpoints; a custom channel mounts whatever you declare with GET/POST/WS from eve/channels.

What is Nitro, exactly? added

Nitro is an open-source server toolkit — the HTTP engine underneath Nuxt, now used standalone by a number of frameworks. Think of it as "Express, but it compiles to a deployment target." You register routes against its router (h3), and at build time it emits a self-contained server bundle for whichever host you're aiming at: a plain Node.js server in .output/, or Vercel's Build Output API format in .vercel/output/, from identical source.

That portability is precisely why eve chose it. The reason eve build && eve start and vercel deploy run the same code is that Nitro absorbs the difference. It also contributes two things eve leans on directly: a scheduled-task runner (which is what actually fires agent/schedules/ on a self-hosted box) and WebSocket support (which is what WS() routes in a custom channel bind to).

What Nitro is not is equally important. It does not know what a session is, it does not store workflow state, and it does not run the sandbox. Those are separate adapters underneath it. Nitro's entire job is: receive an HTTP request, route it to a handler, and expose the workflow entrypoints at /.well-known/workflow/ so the durable runtime can call back in.

2 · The channel normalizes and addresses agent/channels/*.ts

A channel has exactly three jobs: verify and parse the platform payload into a plain message; map the platform conversation onto a session; decide how the reply gets delivered back out.

The addressing part is the subtle one. A channel does not hold a session id — it holds a channel-local address (a Slack thread ts, a phone number, an issue id) and calls from(address).send(text). eve resolves that to whichever session currently owns the address, creating one if nobody does. Exactly one live session may own an address; rekey() moves it.

const source = from(threadId);
await source.send("Hello", { auth });
await source.cancel({ turnId });
await source.reset({ reason: "Start over" });

Security rule that applies to every custom channel: derive the caller from a verified signature or token using constant-time comparison, and never trust an identity field in the request body — it is attacker-controlled.

3 · The session starts a turn durable workflow

A session is the whole durable conversation; it lives 30 days by default (limits.sessionTimeoutMs, or false to disable). A turn is one user message and every model call, tool call, and piece of reasoning it triggers.

Each turn runs as a durable workflow on the open-source Workflow SDK. Locally and under eve start that persists to disk under .eve/.workflow-data; on Vercel the same code runs against Vercel Workflow. You never write workflow code — start() and resumeHook() are runtime implementation details that channels, tools, and hooks never touch.

4 · Steps run and checkpoint the durability unit

A step is one model call plus the tool calls it makes, and it is the unit of durability. eve checkpoints progress and serializes durable state at every step boundary. Your tool code runs inside a managed step, which is why tools, the sandbox, and subagents all feel synchronous despite sitting on a durable substrate.

Some steps don't finish — they park. A human-in-the-loop approval, an interactive OAuth sign-in, or a long-running subagent all suspend the workflow durably, holding zero compute until the click or callback arrives. Days later is a supported case, not an edge case.

5 · The channel delivers back to the platform

Delivery is the channel's decision again — and it is usually not "the client is still holding the request open." Emit runs channel events handlers in process; those handlers call the platform (Slack post, Discord edit, Twilio SMS). Separately, the eve HTTP channel also exposes the durable log as NDJSON on GET …/stream for UIs and SDKs. Two fans of the same log, different transports.

That is the entire extent of eve's relationship to the Chat SDK. Its runtime — Chat, Adapter, Thread — is never imported and is not reachable from eve's public API. Webhook handling, signature verification, event parsing, and thread management are all eve's own. WebSockets, when you use them, are only another edge for a custom channel — never the internal link from workflow to those handlers.

Worked example: tagging the agent in Slack

The abstract contract above is easier to hold once you've traced one real message. Here is everything that happens between @agent what broke the deploy? and the reply landing in the thread.

Why webhooks at all?

Slack is not going to hold a connection open to your server, and your server cannot poll Slack for "did anyone mention me" at any reasonable rate. So the relationship is inverted: you register a URL with Slack once, and Slack does an HTTP POST to you every time something you subscribed to happens. That is a webhook — an inbound call you did not initiate, on a route you published in advance.

For this repo that route is /eve/v1/slack, registered through Vercel Connect with vercel connect attach <uid> --triggers --trigger-path /eve/v1/slack. The --triggers flag is what turns on Slack Event Subscriptions; without it Slack never delivers app_mention or message.im at all, and the agent is silent with nothing in the logs to explain why.

Because anyone on the internet can POST to that URL, the first thing that must happen is proof the request really came from Slack. connectSlackCredentials() returns both halves of that — a webhookVerifier for inbound signature checking and a botToken for outbound calls — which is why this app has no SLACK_SIGNING_SECRET anywhere in it.

The same flow, step by step agent/channels/slack.ts

1. You type @agent what broke the deploy? Slack matches it against your app's Event Subscriptions and POSTs an app_mention envelope to /eve/v1/slack, carrying team_id, event_id, the channel, and the thread_ts.

2. Nitro routes it; the channel verifies it. The signature is checked against Connect's webhookVerifier before anything else runs. Identity is derived from that verified signature — never from a field in the body, which is attacker-controlled.

3. A handler decides whether to answer. Handlers run in strict precedence: onAppMention → onMessage → onEvent → the built-in default, and only the first available one runs. Returning { auth } dispatches, bare null drops the message entirely, and { auth, context } dispatches with extra background injected. { auth: null } still dispatches — the principal is just anonymous (see The inbound gate). eve discards messages authored by the installed app before any of this, so the agent cannot reply to itself in a loop.

4. The thread is resolved to a session. The channel calls from(thread_ts).send(text). If a live session already owns that thread, this is a follow-up turn on the existing conversation with full history. If not, a session is created and takes ownership. Only send() can create one — cancel, compact, clear, and reset never do.

5. The turn runs, and Slack narrates it. The default handlers post Thinking… on inbound, Working… on turn.started, a truncated reasoning snippet on reasoning.appended, and an action label on actions.requested — the tool name plus its most telling argument, like grep useEveAgent. Those are the same stream events described below, just rendered as message edits.

6. The reply is posted. On message.completed the channel posts into the thread, skipping events whose finishReason is "tool-calls" — that filter is what separates the agent's final answer from its mid-turn narration.

events: {
  "message.completed"(eventData, channel, ctx) {
    if (eventData.finishReason === "tool-calls") return;
    if (eventData.message) channel.thread.post(eventData.message);
  },
}

7. If the turn needs a human, it parks. An approval renders as Slack buttons. The workflow suspends holding no compute; clicking a button resumes it. A sign-in challenge is treated as a credential rather than a status, so the public thread gets a link-free note while the actual OAuth URL goes to the triggering user ephemerally.

★
By default the agent sees only the message that mentioned it, not the thread above it. Set threadContext: { since: "last-agent-reply" } to inject the conversation, attributed by Slack user id, and keep repeated mentions incremental instead of re-sending the whole thread each time.

The inbound gate: what stops a request

Message hooks are a gate, not the agent. Side effects you run inside the hook (ctx.reset, ctx.cancel, ctx.thread.post) happen during the webhook. The return value is a separate decision: whether this Slack message becomes a model turn.

ReturnAgent runs?Meaning
null No Drop or consume the message. Bots, ambient chatter, slash commands you handled yourself.
{ auth: null } Yes Dispatch with no principal. auth: null is not “deny” — it is “allow anonymously.”
{ auth: principal } Yes Dispatch with identity (e.g. defaultSlackAuth(message, ctx)).
{ auth, context } Yes Same as dispatch, plus inject extra background into history.

Rule of thumb: null stops; any object with auth allows — even when that value is null.

Side effects vs return value reset · cancel · thread.post

ctx.thread.post(...) is a direct Slack Web API call. It updates the UI immediately and never wakes the model by itself.

ctx.reset({ reason }) retires the session that owns the thread (including an in-flight turn). It does not start a new turn. What you return next decides whether this message is discarded or becomes turn 1 of a fresh session:

// /new as a pure command
await ctx.reset({ reason: "user /new" });
await ctx.thread.post("Started a fresh conversation.");
return null;                    // agent never sees "/new"

// reset, then treat this same message as turn 1 of the new session
await ctx.reset({ reason: "user /new" });
return { auth: null };          // agent sees the message

ctx.cancel() stops the current turn. Cancellation never sends input; return { auth } if the new message should replace it (debounce), or null for a Stop button that only aborts.

PatternIn-flight turnThis message → agent?

cancel + nullstoppedno

The webhook ends early; the turn does not

A webhook is ordinary HTTP with an inverted caller: Slack POSTs you when something happens. Same transport as a REST API; different who initiates.

Two different meanings of “available” get confused here:

  • The route must be reachable. Production must accept new POSTs to /eve/v1/slack. If the deployment is down, Slack retries or drops events — same as any public API.
  • One request does not last the whole agent turn. The webhook can return 200 in seconds (“got the event, work started”). The durable workflow keeps running, parks for HITL, survives redeploys, and later posts back via separate HTTP calls to Slack’s Web API. Progress and the final answer are not the body of the original webhook response.
t=0    Slack POST /eve/v1/slack          ← request A (brief)
       verify · onMessage · start turn
       respond 200 OK to Slack

t=1s   workflow still running             ← not request A
t=5s   events → Slack "Working…"          ← outbound REST
t=20s  events → Slack final answer        ← outbound REST

Contrast the browser/HTTP channel: GET /eve/v1/session/:id/stream can hold an NDJSON connection open while tokens stream. Slack’s path is webhook-in, REST-out — no persistent Slack↔eve socket for the normal case.

channel.events are in-app callbacks, not listeners

Nothing on Slack “subscribes” to your agent stream. When the durable turn emits turn.started or message.completed, the eve runtime invokes a function you registered on the channel. That function then calls Slack over HTTP if it wants the UI to update.

Agent turn emits message.completed
        │
        ▼
  channel.events["message.completed"] ?
        │
   you wrote it ──────────► your function (log, post, metrics…)
   you didn't   ──────────► defaultEvents["message.completed"]
                            (post reply in thread, skip tool-calls)

That is the same shape as an onClick registry — not a network listener and not a second process. It is also not the same thing as agent/hooks/: those are observe-only stream subscribers that cannot decide delivery. Channel events own how this surface shows progress and replies.

Default delivery map + how to extend it eve/channels/slack · defaultEvents

Defaults are exported. Prefer composing over reverse-engineering:

import {
  slackChannel,
  defaultEvents,
  defaultSlackAuth,
} from "eve/channels/slack";

export default slackChannel({
  credentials: connectSlackCredentials("slack/eevee"),
  events: {
    ...defaultEvents,
    async "message.completed"(eventData, channel, ctx) {
      await logSomewhere(eventData);           // your side effect
      return defaultEvents["message.completed"]?.(eventData, channel, ctx);
    },
  },
});

Overriding a key replaces that event’s default. If you omit the call into defaultEvents, you also own Slack delivery for that event.

What durability actually buys you

Kill the process, hit a timeout, or redeploy mid-turn, and the run resumes from the last completed step. Completed steps never re-execute; eve replays the recorded result from its journal. Crash recovery, redeploys, and resuming a parked turn therefore emit nothing new to the stream at all.

The exception is the one you have to design around: a step interrupted mid-execution re-runs, and eve will run a durable step up to four times.

★
Make non-idempotent side effects — charges, emails, outbound posts — idempotent, or gate them behind an approval policy. Everything the interrupted attempt already wrote to the stream stays there, and the retry emits its own events with fresh ids, so a consumer sees both attempts and nothing records which one won.

How that is actually achieved

Yes — durable functions, in the specific sense Temporal and Azure Durable Functions mean it. The mechanism is event-sourced deterministic replay, and the thing that makes it click is realizing that nothing is ever "frozen and thawed." No stack is serialized, no continuation is captured, no process is held open. There is only an append-only log and a function that can be re-run against it.

The journal is that log. In the Workflow SDK's World interface, storage has exactly one write path — events.create() — and the runs, steps, and hooks you can query are materialized views over it, not independently mutable records. The vocabulary is small:

run_created   run_started   run_completed  run_failed  run_cancelled
step_created  step_started  step_completed step_failed step_retrying
hook_created  hook_received hook_disposed  hook_conflict
wait_created  wait_completed                attr_set

A step writes step_started before its body runs and step_completed (with the serialized result) after it settles. Those two bracketing events are the entire durability guarantee.

What physically happens when a crashed run resumes @workflow/core/runtime

A fresh runtime is instantiated and the workflow function re-executes from the top. It does not resume at the line it died on — that line no longer exists anywhere. As execution walks forward, each await on a step consults the journal: if a step_completed event is already recorded, the awaited value resolves instantly from the log and the step body never runs. The first step with no terminal event is the first thing that actually executes.

So "picks up from the last completed step" and "re-runs from the top" are both true, at different layers. The function body genuinely replays; it is simply near-free to do so, because everything already settled short-circuits. This is why an interrupted step re-runs and a completed one never does — the interrupted one wrote step_started but no terminal event, so replay treats it as never having happened.

It is also why crash recovery emits nothing to your event stream. Replaying a completed step produces its recorded result without re-entering the body, and the body is what emits.

The determinism tax you pay for it workflow-sdk.dev

If the function is re-executed on every invocation, it has to make the same decisions every time — otherwise replay walks a different path than the journal describes. That is the constraint the whole model rests on. Anything non-deterministic or side-effecting belongs inside a step, whose result gets journaled, rather than in workflow scope.

Worth correcting a common assumption: the SDK does not forbid Math.random() and Date in workflow scope — it seeds and fixes them, so they return the same values on every replay and are safe to use. Genuine I/O is the thing that must move into a step; workflow scope has no fetch, no timers, and no Node built-ins.

In eve you mostly don't feel this, because you never write workflow code. eve's own turn loop is the workflow, and your tool bodies run inside managed steps — which is exactly why a tool can do arbitrary I/O and still sit on a durable substrate.

Parking, retries, and worlds @workflow/core, @workflow/world

Parking is a thrown signal. When the function awaits something with no corresponding journal entry — a pending approval, an OAuth callback — the runtime throws a WorkflowSuspension carrying the list of pending operations. The handler durably records hook_created / wait_created, and then the process simply exits. Nothing in memory represents "waiting"; the suspended state is the log plus a pending hook row. That is the literal meaning of holding no compute.

Waking is the mirror image: resumeHook(token, payload), called from an ordinary route handler, writes hook_received and enqueues a dispatch. The next invocation replays, reaches the same await, finds the event now present, and continues.

Retries. DEFAULT_STEP_MAX_RETRIES = 3 — which is where "up to four times" comes from: one initial attempt plus three retries. Attempt count isn't a counter, it's derived from how many step_started events the log already holds for that step. Throw FatalError to skip retries entirely, or RetryableError with a retryAfter to back off a rate limit.

A world is the pluggable backend for all of this: World extends Queue, Streamer, Storage. Storage is the event log, Streamer backs the event stream, Queue dispatches invocations. It advertises a specVersion the runtime gates on, plus capability flags so the core enables optimizations only where supported. eve ships @workflow/world-local (on-disk, dev and self-host) and @workflow/world-vercel; its docs name @workflow/world-postgres as an alternative, though that one isn't pinned in this repo's dependency tree.

Concurrent writers are handled by optimistic concurrency: writes carry a precondition on the log's state, so a stale replay racing a live one is rejected with a 412 rather than corrupting the journal.

On Vercel, a production deployment change takes effect on the next model turn of an existing session: new instructions, model, and tools, with conversation history and authored state intact. Identity-based channels like a Telegram private chat adopt agent updates without needing a new session.

Two runtimes, one trust boundary

An eve agent spans two execution environments, and the split is a security boundary rather than a performance one.

 App runtimeSandbox
secrets / envyesnone
Node.js codeyesno
networkunrestrictedpolicy-controlled
filesystemthe app's ownisolated /workspace
runsagent loop, model calls, tool executors, hooks, connectionsthe model's shell and processes

Provider keys, tool secrets, and MCP/OpenAPI/connection credentials stay in the app runtime and are resolved per step — never serialized into durable state, never placed in conversation history. When sandboxed code needs authenticated network access (cloning a private repo, say), credential brokering injects the auth header at the sandbox's network firewall for matching domains. The secret never enters the sandbox process; only the response does.

The two have decoupled lifetimes. A parked workflow holds no sandbox compute, and the sandbox is keyed per durable session rather than per deployment — a redeploy does not discard it. Only an actual change to the sandbox definition forces a rebuild.

★
Counterintuitive: read_file, write_file, glob, and grep do not execute in the sandbox. They run in the app runtime and proxy into it. Only actual shell commands run inside. The upside is that all sandbox work flows through app-side tools, so it inherits the same approval and instrumentation path as any other tool call.

So what actually runs in the sandbox?

A Linux machine with a shell. Not a JavaScript VM, not a Python interpreter — a real filesystem rooted at /workspace and a real bash, from the published ghcr.io/vercel/eve:latest image. Whatever binaries that image carries are what the model has: git, node, python, package managers. The model isn't handed a language; it's handed a command line and picks whatever suits the task, exactly as you would over SSH.

Which is to say the answer to "does it run JS or Python?" is both, or neither — it runs commands. If the model wants Python it writes a .py file and runs python on it. Your agent/tools/*.ts files never go near it; those execute in the app runtime with your secrets.

the model wants to…what happens
explore a repobash: git clone … then glob / grep over the result
crunch a CSVwrites analysis.py, runs python analysis.py, reads stdout
check its own workbash: npm test — and can iterate on a real failure
run a serverspawn() keeps it alive while the turn continues; kill() ends it
produce a file for youwrites to /workspace, which survives every turn of the session

Where it physically runs depends on the backend, resolved by defaultBackend() in priority order: Vercel Sandbox when deployed on Vercel, then Docker if a daemon is reachable, then microsandbox (a local VM, macOS on Apple Silicon or Linux with KVM), and finally just-bash — a pure-JS simulated shell with a virtual filesystem and no real binaries at all. That last fallback is worth knowing about, because an agent that works in production and mysteriously can't find git locally has usually landed on it.

The sandbox exists to give the model a place to be wrong safely. It holds no process.env, no secrets, and no route back into the app runtime, so a destructive command or a prompt-injected instruction damages a disposable /workspace and nothing else. Egress defaults to allow-all, which is the setting to change first for anything sensitive — "deny-all" or an explicit allow-list, set on the backend factory or in onSession.

What you author

Six surfaces, each a directory under agent/. The distinction that matters most is tools versus skills: a tool is a typed action with runtime behavior; a skill is a procedure written in markdown. Loading a skill adds instructions to context and never adds execution surface.

The default harness

Before you author anything, every agent already has a tool set: bash, read_file, write_file, glob, grep, web_fetch, web_search, todo, and ask_question. Three more appear conditionally — agent only in the root session, load_skill only if skills are declared, connection_search only if connections are. Authoring a file at a built-in's slug overrides it; exporting disableTool() removes it. A filename that matches no known built-in is a build error rather than a silent no-op.

Compaction is part of the harness too. When the conversation plus its checkpoint envelope crosses compaction.thresholdPercent (default 0.9), eve summarizes older turns and preserves framework tool state across the boundary automatically.

The isolation rules

Delegation in eve is deliberately non-transitive, and the defaults are stricter than most people assume. There are two mechanisms.

The built-in agent tool delegates to a copy of the root agent: it inherits instructions, connections, auth, and the same sandbox, but gets fresh conversation history and fresh state. A declared subagent under agent/subagents/<id>/ inherits nothing from the root's authored slots — an absent slot falls back to the framework default, not the parent's version.

A subagent boundary is a context boundary, not a permission boundary. A sensitive tool still needs its own approval policy on the other side of it.

One stream for everything

Every observable thing a run does lands on a single newline-delimited JSON log: turn.started → step.started → actions.requested → action.result → message.appended… → turn.completed → session.waiting. That log is the source of truth. How different pieces of the system see it is not the same for everyone — and that distinction is the part people usually get wrong.

Emit is a trigger, not a message queue

When the harness reaches a lifecycle moment, it calls emit. Emit does two jobs that look similar from the outside but are completely different under the hood:

  1. Append the stamped event to the durable session stream (Workflow world's streams.write — an append-only log).
  2. Call registered handlers in memory, same process, same stack of awaits: channel events first, then metadata projection, then agent hooks, then dynamic resolvers.

There is no SQS, no RabbitMQ, no worker that later dequeues message.completed and runs your Slack post. Channel handlers and defineHook bodies are ordinary async functions on the emit path — closer to an ordered EventEmitter that happens to journal every event first than to a broker.

Dispatch order is structural sessions-runs-and-streaming added

Every stream event runs four steps, always in this order:

1. channel events["…"] handler   // may mutate adapter state
2. metadata projection             // re-eval channel.metadata(state)
3. authored hooks                  // agent/hooks/*
4. dynamic resolvers               // tools / skills / instructions

By the time a hook or resolver reads ctx.channel.metadata, the channel has already updated its state and the projection is current. That is why Slack can post a typing indicator on turn.started without a separate fan-out pipeline: the channel is not subscribed to the HTTP stream; it is invoked as the first step of emit.

Channel handlers and agent hooks are structurally the same shape. Use the channel map for adapter-specific delivery (post to Slack, edit a Discord message). Use defineHook for agent-wide observation (audit, metrics) that should fire no matter which channel started the session. Both fire when both are registered; neither dequeues from a broker.

If you know SQS or RabbitMQ comparison added

SQS is a competing-consumer queue: long-poll for work, process, delete. Messages leave the queue for other workers once taken.

RabbitMQ is a broker that pushes over a persistent AMQP connection; consumers ack deliveries. Fan-out is a routing choice you configure.

Eve's session stream is an append-only log (many readers can follow from a cursor; nothing is deleted on read) plus inline side effects on emit for channels and hooks. External clients hold an open HTTP NDJSON response and reconnect with startIndex when the transport drops — more like tailing a journal than claiming a work item.

There is queue-shaped machinery elsewhere — the session's command inbox, Workflow dispatch for steps and parked hooks — but that moves turns and steps, not "deliver this stream event to channel handlers."

Where WebSockets actually fit WS() routes added

WebSockets are an optional edge transport for custom channels, not the bus between workflow and channel handlers. A WS() route still ends in from(address).send(text) on inbound — the same entry the Slack webhook uses. Outbound over that socket is your job if you want it (write frames from an events handler); eve does not auto-pipe the workflow stream over the socket.

The default eve surface is HTTP: POST to create/send, GET …/stream for NDJSON. Platform channels (Slack, Telegram, Twilio) are webhook in and platform HTTP API out. Prefer WS() lifecycle hooks over createWebSocketUpgradeServer(), which exists only for third-party SDKs that insist on binding Node's upgrade event.

What is NDJSON? added

Newline-Delimited JSON: one complete JSON value per line, separated by \n. The file or response as a whole is not valid JSON — it is a sequence of independent JSON documents. Content type application/x-ndjson.

{"type":"turn.started","data":{...},"meta":{...}}
{"type":"message.appended","data":{"messageDelta":"It is "},...}
{"type":"message.completed","data":{...},"meta":{...}}

The reason to use it instead of a JSON array is that an array can't be consumed until it closes. A reader has to wait for the final ] before the parser will hand back anything, which is useless for a response that stays open for minutes. With NDJSON a consumer splits on newline and parses each line the moment it arrives — so tokens appear as the model produces them. Equally important, the writer never has to hold the whole document in memory or know in advance how many events there will be.

You may know the same idea as JSON Lines (.jsonl); they are the same format under two names. The obvious alternative here would have been Server-Sent Events, and eve's stream carries the same information, but NDJSON has no data: field framing to strip, works identically for a curl pipe and a file on disk, and imposes nothing browser-specific — this stream is read as often by a server-side ingest job as by a UI.

Two identities, kept apart on purpose

The HTTP API speaks only durable session ids. Channel addresses stay behind the channel boundary and are never accepted or returned by /eve/v1/session*. That separation is why a Slack thread can outlive a session reset, and why an HTTP client cannot reach into a platform conversation it was never given.

From dev to production

The loop is eve info → eve dev → eve build → eve start. eve dev boots the server and the terminal UI together; pointed at a URL instead, it drives a deployed agent from your terminal, which is the fastest real smoke test there is.

The two hosts differ in exactly three places: where the build output goes (.vercel/output vs .output/), which Workflow world backs durable state (Vercel Workflow vs the SDK's local on-disk world, or a package like @workflow/world-postgres selected through experimental.workflow.world), and which sandbox backend defaultBackend() resolves to. Everything above those adapters is identical.

Gotchas worth knowing

  • There is no durable message queue per session. An ID-addressed delivery and a channel delivery both target the session's current command inbox, which the runtime drains best-effort at workflow boundaries and may fold several deliveries into one turn. Send one turn at a time and wait for session.waiting. If your channel can receive bursts, keep your own per-session queue in the channel layer.
  • Channel handlers are not queue consumers either. They run in memory on the emit path after the event is appended to the durable log. Do not model Slack delivery as "subscribe to the stream and post" — model it as "emit invokes events["message.completed"], which posts." Retries re-emit under new meta.ids, so those handlers can run again; make outbound posts idempotent.
  • WebSockets are not the workflow↔channel bus. Optional custom-channel edge only. Default clients use HTTP NDJSON; Slack-class platforms use webhooks + REST.
  • meta.id dedupes reconnects, not retries. A retried step re-emits under new ids carrying the same turnId, stepIndex, and sequence. Key idempotency on those coordinates; key stored rows on meta.id.
  • Omitting approval means the tool runs unsupervised. The default is never(). Approval is opt-in, so a tool that charges a card or sends an email needs once() or always() written explicitly.
  • placeholderAuth() is not auth. The scaffolded chain in this repo returns a setup-focused 401 in production by design. Nothing reaches the agent from a browser until it is replaced with Clerk, Auth.js, or your own verifier.
  • Skills and state never cross an agent boundary. A subagent's skills are invisible to the root and vice versa, and defineState is never shared with any subagent. Share code through lib/; share data through an external store.
  • eve dev never fires schedules on cron. Dispatch them manually via the dev-only route POST /eve/v1/dev/schedules/:id. In production, a host that serves HTTP without Nitro's scheduled-task runner compiles fine and then silently never fires them.
  • instructions.ts runs once, at build time. Being TypeScript, it looks per-session, but eve captures the resulting markdown into the compiled manifest and serves the same prompt to every session forever. Genuinely per-caller instructions need defineDynamic.
  • A self-host proxy must forward /.well-known/workflow/ too. Forward only /eve/ and a session will start and then stall — the workflow callbacks have no way back in.
  • Tool output crosses a JSON boundary. No Date, Map, Set, NaN, or cycles. Images must be base64, and compaction replaces file payloads with a text stub — an image is unrecoverable afterwards.
  • { auth: null } is allow, not deny. The gate is the shape of the return: bare null drops the message; an object with an auth field dispatches. A null principal only means anonymous — the agent still runs.
  • Overriding events["message.completed"] replaces delivery. Spread defaultEvents and call through, or you will log the answer and never post it to Slack. Channel events are not the same as agent/hooks/.

FAQ

Do I need a channel file to have an HTTP API?
No. /eve/v1/session* is mounted by default. You add agent/channels/eve.ts only to override defaults, which in practice means the auth policy or CORS.
How does a Slack thread find its session again?
The channel calls from(threadTs). eve looks up the session that currently owns that address and creates one only if nobody does. Ownership is exclusive and movable with rekey().
Is a webhook different from a REST API?
Same HTTP. Different who calls whom. REST is usually client → you on demand. A webhook is provider → you when an event happens (Slack Events API → /eve/v1/slack). Outbound replies are ordinary REST the other way: your app → Slack Web API.
Does the webhook stay open until the agent finishes?
No. The inbound request can return quickly after the turn is started. Status updates and the final reply are later outbound calls from channel events handlers (or thread.post) while the durable workflow runs independently.
What is the difference between return null and return { auth: null }?
null stops the request — no agent turn. { auth: null } allows it with no authenticated principal. Use the latter for DMs/mentions when you do not need a stamped Slack identity; use defaultSlackAuth when you do.
Where do “Thinking…” and “Working…” come from?
Default channel events (exported as defaultEvents) map stream events to Slack typing/posts. They run in-process when the runtime emits those events; they are not Slack-side listeners. Wrap them when you need logging or custom UX.
What happens if I redeploy while a turn is running?
The run resumes from the last completed step. Completed steps replay their recorded result and emit nothing; only a step that was mid-execution re-runs.
Is a turn cancellation a failure?
No. cancel is cooperative and returns "accepted" the moment it is durably queued. You confirm it on the stream as turn.cancelled followed by session.waiting, never as a failure event, and the session accepts the next message normally. Active subagents are cancelled recursively first.
Where does state live when I'm not on Vercel?
The Workflow SDK's local world persists runs to disk under .eve/.workflow-data and dispatches through the same Nitro-hosted workflow routes. Self-hosted deployments can swap in another world package — @workflow/world-postgres, for instance — via experimental.workflow.world in agent.ts.
Can the model reach my API keys?
No. Secrets live in the app runtime; the sandbox has no process.env, no Node.js, and no path back. When sandboxed code needs authenticated network access, the credential is injected at the firewall rather than handed to the process.
Is emit like SQS / RabbitMQ for channel delivery?
No. Emit appends to an append-only log, then awaits channel handlers and hooks in process. There is no competing-consumer queue and no broker push for those handlers. External UIs follow the log over HTTP NDJSON; platform delivery is whatever the handler does next (usually a REST call).
When would I use WS()?
When your custom surface genuinely needs a duplex socket (voice, proprietary client). Inbound still becomes from(address).send(…); outbound frames are yours to write from events if you want them. Prefer that over inventing a second internal event bus.
