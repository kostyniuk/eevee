Trace one pull request into one advisory review

TL;DR — The GitHub App decides where eevee may act; onPullRequest() decides when it acts; the reviewer prompt and Zod schema decide what shape the model may return; and the Reviews API decides how that result appears in GitHub. The edge eval proves the whole chain, while vercel deploy --prod ships the current source snapshot independently of commits or pull requests.

The mental model: a chain of contracts

Your tangible win is to predict the outcome of a pull-request event by locating the contract that controls it. Do not think of eevee as one large “AI reviewer.” Think of it as a short chain where every boundary rejects, transforms, or delivers data.

installation→webhook→gate→model→schema→GitHub review
01
Useful debugging rule: find the first boundary whose expected output is missing. Everything after it is downstream noise.

Trace one event

Open the steps in order. Only the first is expanded so you actively retrieve the rest instead of passively scanning them.

1 · GitHub grants a location GitHub App installation

The App is installed on a personal account or organization, then granted either all repositories or selected repositories. That installation—not the code—defines eevee's repository reach. GitHub documents both scopes in its installation guide.

2 · eve authenticates ingress github.ts:9–24

connectGitHubCredentials("github/eevee") supplies the installation credential and webhook secret. eve owns the /eve/v1/github route and signature verification; our handler opts into pull-request events. The local eval swaps in deterministic credentials, but production uses the managed connector. See the eve GitHub integration.

3 · The gate admits one event github.ts:23–31

onPullRequest() returns work only when the action is opened and the pull request is not a draft. Returning null ends the chain before a model call. This is the cheapest and clearest place to express event policy.

4 · The model crosses a typed boundary reviewer.md + review.ts

The reviewer instructions constrain behavior and request exact JSON. reviewSchema.parse() then treats that output as untrusted input. A rating of 3 or more removes inline findings even if the model supplied them, so application code—not prompt compliance—enforces the safety threshold.

5 · GitHub receives a formal review github.ts:43–55

The completed message becomes POST /pulls/{number}/reviews. The payload uses event: "COMMENT", an advisory summary, the reviewed commit SHA, and any permitted inline comments. GitHub's review endpoint distinguishes COMMENT from APPROVE and REQUEST_CHANGES.

// What counts as a valid review?

if (review.safetyRating >= 3) return { ...review, findings: [] };

Prove behavior at the edge

The eval does not call a helper and assume the route works. It signs a synthetic GitHub webhook, sends it to /eve/v1/github, and captures the outbound REST request. That covers both edges of our system.

InputExpected edge outputBoundary proved
Safe, opened PROne COMMENT review; no inline findingsFull chain + high-rating rule
Risky, opened PROne COMMENT review; anchored findingSchema + line mapping
Draft PRNo outbound reviewAdmission gate

The harness checks authorization, endpoint, body, and comments in the actual eval code. Deterministic model fixtures keep this a contract test rather than a test of model mood.

Why production did not need a merge request

Git history and deployment input are separate mechanisms. A Git-integrated deployment starts from a pushed commit. A Vercel CLI source deployment starts from the files in the local project directory.

# upload the current local project and assign the production domain
vercel deploy --prod --yes

Vercel explicitly documents that CLI production deployment works whether the project is connected to Git or not. The tradeoff is traceability: production can contain a source snapshot that no commit names. A safer staged variant is vercel --prod --skip-domain, followed by an explicit promotion after inspection. See Vercel's CLI deployment guide.

Gotchas worth knowing

  • A valid webhook is not an authorized review. Signature verification establishes origin; the installation token and repository grant establish where the App may act.
  • A prompt is not a runtime contract. Zod parsing and the rating threshold enforce what must remain true when model output is imperfect.
  • A production deployment is not proof of Git history. CLI deployment can ship uncommitted local source, which is useful but less traceable.

FAQ

Is the agent connected per repository or per account?
The GitHub App is installed on an account or organization, with access granted to either all repositories or selected repositories. “Selected repositories” gives per-repo availability without creating a different App.
Why use a formal review instead of an issue comment?
The Reviews API groups the summary and line-anchored findings into one review tied to a commit. COMMENT preserves that structure without approving or requesting changes.
